# SecureVault follow-up audit and repairs

Date: 2026-10-06. The follow-up initially reran 101 backend tests, nine frontend tests, lint, build, browser smoke and both dependency audits. Those passed, but additional probes and review found cases the suites missed. The user then requested repairs. The issues below are addressed in the project and have regression coverage where appropriate.

The original Critical findings remain covered: password bypass fails, no demo account is seeded, and audit reads are limited to the authenticated user. The original finding-by-finding mapping is in [AUDIT_FIXES.md](AUDIT_FIXES.md). No new Critical issue was confirmed in this follow-up. Passing checks do not establish that every possible defect has been eliminated.

## Findings and resolutions

| Severity | Location | Problem and impact | Implemented fix and evidence |
| --- | --- | --- | --- |
| High | `backend/routes/auth.js`, `backend/store/database.js`, registration/login pages | Unfinished enrollment exposed its stored authenticator secret after a password-only login. A signup started with another person's email and an attacker-chosen password could become an account takeover if the recipient claimed the link. The pre-fix in-memory probe obtained the same secret and a full session. | Email claims now require the initiating password. Password-only login exposes no setup token/secret and sends a fresh email proof for unfinished enrollment. Claiming that proof rotates the secret and invalidates prior enrollment challenges. Schema upgrades invalidate legacy enrollment challenges. Tests cover unsolicited claims, incorrect passwords, fresh proof, rotation, old-challenge rejection and completed enrollment. |
| High | `frontend/src/components/TransferForm.jsx`, transaction API/routes | Retry keys existed only inside the transfer component. Navigation or reload could lose an unresolved request and allow another key for the same intended payment. Closing a tab lost all component/session state. | Pending details are saved before sending in user-scoped session storage. Only an opaque key goes into persistent local storage. An authenticated, user-scoped, masked result endpoint retrieves committed outcomes without another payment. Missing outcomes retain the original key. Ref guards, payment Web Locks and outstanding-key checks prevent another unresolved payment in a cooperating browser. Unit and browser tests deliberately lose committed responses, navigate/reload/retry, close/reopen a tab and block another tab's new submission. Balances confirm one debit. Clearing browser storage or using a different device still requires checking server transaction history before manually creating a new intent. |
| High, vendor-confirmed runtime risk; no app-specific exploit attempted | Dockerfile, package engines/lockfiles, runtime pins, CI | Node 24.15 was pinned despite later security releases. `npm audit` does not audit the Node executable or container OS. | Docker, CI, `.nvmrc` and `.node-version` pin 24.21.0; package engines require 24.21 or later, and production rejects older runtimes. The portable Windows runtime used for final tests was downloaded from Node's official distribution and SHA-256 checked. Official Node/Docker sources are linked below. The machine's default Node installation remains 24.15; select/install the required version for ordinary local commands. |
| Medium | `frontend/src/api/client.js`, `frontend/src/api/authApi.js` | Two tabs could submit the same refresh cookie concurrently. The pre-fix probe returned 200/401, then the newly issued access token also returned 401 because refresh reuse revoked the session. Other tabs retained their signed-in UI after logout. | Refresh holds a same-origin Web Lock until the response/cookie update completes. Module-level deduplication still handles one tab. BroadcastChannel propagates sign-out and final session expiry. Real concurrent-tab restoration and cross-tab sign-out pass in Edge. Server-side refresh reuse detection remains strict. Legacy browsers without Web Locks retain only single-tab serialization; use a current HTTPS browser. |
| Medium | `frontend/src/hooks/useTransactions.js`, transactions API/routes | A failed page advanced the offset before success, so retry skipped records. Rapid load clicks could also skip a page. Category filters covered only already-loaded rows. | Offsets advance after success; failures retry the same page and clear their error on retry. A synchronous ref blocks simultaneous loads, generations reject stale results and initial requests use cancellation signals. Category filters query the server's complete history and reset pagination. Unit and browser checks verify offsets 20,20 after a failed load. |
| Medium | `frontend/src/components/TransferForm.jsx` | A definitive rejection remained set after going back and editing, leaving authorization disabled. Cooling-off completion depended on another input event to rerender. | Reviewing edited details clears the rejection state. An active timer updates availability and stops after the deadline. Tests verify that a rejected amount can be changed and sent, and cooling off unlocks automatically. |
| Medium | `backend/store/database.js`, `backend/services/mailService.js`, `backend/server.js` | The dispatcher could send a proof after its 30-minute expiry; this was reproduced before the fix. A stale lease owner could mark a newer attempt sent. Shutdown could close the database before an in-flight mail operation finished. | Dispatch discards expired/claimed proofs, leases jobs for two minutes and acknowledges only the matching attempt. Shutdown drains delivery before database closure. The application has a 45-second shutdown deadline and Compose a 50-second grace period. Mock-transport tests cover expiry, stale leases, successful delivery, safe error logging and draining. Delivery remains at least once after provider/worker failure; proof claims remain single-use. |
| Medium | `backend/app.js` | Unsupported content encoding returned 500 instead of 415; the pre-fix probe reproduced it. Other parser/router client errors were not preserved. Missing assets could receive the SPA HTML with status 200. | Valid 4xx error statuses are preserved with generic messages. Tests cover malformed URLs, unsupported encoding, malformed JSON and oversized bodies. Missing asset paths return 404; application routes retain SPA fallback. |
| Medium | `backend/store/database.js`, `backend/app.js` | Readiness checked only `SELECT 1`. With a wrong encryption key, the pre-fix probe got readiness 200 and login 500. | An encrypted key-verification record is validated at startup and readiness. Old databases decrypt an existing record before establishing it. Wrong keys fail startup/readiness; tests cover both and a valid-key recovery. Readiness is not a full scan of every encrypted record. |
| Medium | `backend/scripts/backup.js` | Backup called the normal create/migrate store factory, so a missing/mistyped source could become an empty database and a seemingly successful backup. The destination existence check also did not exclusively reserve the file. | Backup requires an existing source, opens it read-only, checks SQLite integrity/application schema, refuses project-local destinations and reserves the target with exclusive creation. Failed backups remove only their reserved incomplete destination. Tests cover usable consistent snapshots, overwrite refusal and missing-source refusal without creating either file. |
| Medium | `backend/config/index.js`, Compose | A mistyped environment silently became development mode; invalid server/mail ports passed validation. Case-variant copies of the same hex secret passed distinctness checks. | Environment values and port ranges are validated; hex keys are canonicalized before checking distinctness; trusted origins accept surrounding list whitespace. `loadConfig` respects the supplied data directory. Compose explicitly sets production mode and port. Tests cover invalid values and duplicated keys. |
| Low, financial integrity hardening | `backend/store/database.js`, `backend/scripts/reconcile.js` | HTTP validators protected public transfer amounts, but direct store callers lacked the same integer-cent guard. Transaction records lacked an integer-type insert guard and remained mutable. There was no reconciliation command. This was not a demonstrated remote attack. | Store calls reject nonpositive/fractional/unsafe cents. Database triggers enforce transaction cents and append-only transaction history. Reconciliation reports unexplained account balances, unbalanced references and transaction records without matching ledger entries. Tests cover safe/unsafe amounts, append-only records, fractional inserts, valid reconciliation and deliberate corruption. Run `npm run reconcile --prefix backend` in operations. |
| Low | Dashboard, account hook, styles | Fixed sidebar/grid widths compressed narrow screens. Collapsing navigation removed the visible logout control. Icon-only controls lacked names, some small text had poor contrast, and transfer icons contained literal question marks. The displayed update time changed on every render rather than each successful account fetch. | Responsive grids/sidebar/padding, labeled navigation and toggle, `aria-current`, accessible logout in both widths, brighter text/account colors, repaired icons and reduced-motion styles. Update time now records the successful fetch. Account requests use their AbortSignal. Errors and empty states have clear feedback/retry controls. Edge checks the 390-pixel layout and collapsed logout. This is not a complete WCAG conformance certification. |
| Low | Auth context and login/registration pages | Late registration/claim/recovery responses could restore stale pending state. Login reset did not invalidate the previous generation; UI buttons could switch flows during verification. Rapid form submissions relied only on React state. | Generation checks protect asynchronous state changes, reset invalidates the generation, flow-switch controls are disabled during verification and ref guards block immediate repeated submissions. Tests cover late restoration/claims and check-email responses without a password challenge. |
| Low | CI, Dockerfile, Compose, operation guides | Browser regressions and Docker builds were absent from CI. Container data permissions and shutdown grace were not aligned with the application. Caddy used a floating major-version tag. | CI now installs Chromium and runs browser regressions plus a separate Docker build. Data directory/file and backup POSIX permissions are restricted; the API uses an init process, drops capabilities and prevents privilege escalation. Caddy is pinned to 2.11.7-alpine, confirmed against the official image listing. Setup, API-flow, migration, reconciliation and mail guidance are updated. Local Docker execution was unavailable. |

The injected SQL-failure regression deliberately produces one generic server-error log while asserting complete rollback. Jest's VM Modules warning is expected for the current authenticator module. Neither indicates a failed test.

Tests used disposable users, temporary databases and local browser contexts. No existing customer funds were moved and no external mail or deployment was sent. The production-mode test uses an empty mail queue and an invalid placeholder SMTP host; it does not validate provider delivery.

## Deployment work that remains external

- Select Node 24.21.0 or a supported later patched release for local execution. The project pins and production guard are updated; the system-wide installation was not replaced.
- Run Docker/Compose on the target host, validate Caddy HTTPS/DNS and the private environment file, and execute the new CI workflow in a repository. Docker is not installed in this workspace, so container build/startup and Linux permission behavior were not tested locally.
- Configure the real SMTP provider and validate TLS/authentication, inbox delivery and operational alerts. Mail transport behavior was tested with a mock; no provider was contacted.
- Schedule protected backups, rehearsal restores, reconciliation, disk/outbox monitoring and financial-history archival. Readiness verifies database/key access rather than ongoing full reconciliation.
- SQLite remains a shared local-file, single-host design. Independent hosts require a server database. External settlement, identity/fraud/compliance integrations remain the boundaries documented in README; no external payment operation is enabled.

These are environment/integration requirements, not claims that a deployment has been completed. Financial state, audit and idempotency are retained; users who erase browser storage or change devices should check transaction history before manually repeating an uncertain payment.
